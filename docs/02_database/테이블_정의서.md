## 1. 테이블 정의

표기: PK 기본키, FK 외래키, UQ 유일, NN 필수(NOT NULL). 외래키는 따로 적지 않으면 삭제를 막는다(`RESTRICT`). 회원 데이터 테이블의 `member_id` 외래키는 `ON DELETE CASCADE`이다.

### 1.1 회원

#### member (회원)
|컬럼|타입|제약|설명|
|--|--|--|--|
|member_id|NUMBER|PK, IDENTITY|회원 번호|
|login_id|VARCHAR2(20)|UQ, NN|회원 아이디(영문 대/소문자, 숫자)|

### 1.3 확률·천장 규칙

#### pity_group (천장 묶음)
|컬럼|타입|제약|설명|
|--|--|--|--|
|pity_group_id|NUMBER|PK, IDENTITY||

#### gacha_rule (확률·천장 규칙)
|컬럼|타입|제약|설명|
|--|--|--|--|
|rule_id|NUMBER|PK, IDENTITY||
|game_id|NUMBER|FK(game), NN||
|name|VARCHAR2(100)|NN||
|pity_scope|VARCHAR2(10)|NN, CHECK('GROUP','BANNER')|`GROUP`은 묶음 안의 배너가 천장을 공유, `BANNER`는 배너마다 따로 센다(배너가 끝나면 초기화)|
|pity_group_id|NUMBER|FK(pity_group)|`GROUP`일 때 필수, `BANNER`일 때 비움|
|pity_rarity_id|NUMBER|FK(rarity), NN|천장이 적용되는 등급(6성)|
|pity_start_count|NUMBER|NN|이 횟수만큼 연속으로 못 뽑으면 다음 뽑기부터 확률이 올라간다(50)|

|description|VARCHAR2(1000)||인게임 확률 안내 요약|
|active|CHAR(1)|NN, 기본 'Y'||

확률이 100%가 되는 횟수는 기본 확률, 시작 횟수, 올라가는 확률로 계산한다(예: 2% → 50회 후 4%, 6%, … → 99번째 100%).

#### rule_rate (등급별 기본 확률과 픽업 몫)
|컬럼|타입|제약|설명|
|--|--|--|--|
|rule_id|NUMBER|PK, FK(gacha_rule)||
|rarity_id|NUMBER|PK, FK(rarity)|규칙마다 등급당 한 행. 등급 수는 게임마다 다를 수 있어 컬럼이 아니라 행으로 둔다|
|base_rate|NUMBER(5,2)|NN, 0~100|기본 확률(6성 2, 5성 8, 4성 50, 3성 40). 한 규칙의 합은 100(Sec-005)|
|share_rate|NUMBER(5,2)|NN, 기본 0, 0~100|그 등급 확률 중 픽업 캐릭터들이 나누는 몫(표준 6성 50, 5성 50, 픽업이 없는 등급은 0). 몫은 `banner_pickup.weight` 비율로 캐릭터에게 나눈다|

|컬럼|타입|제약|설명|
|--|--|--|--|
|guarantee_id|NUMBER|PK, IDENTITY||
|rule_id|NUMBER|FK(gacha_rule), NN||

|rarity_id|NUMBER|FK(rarity)|대상 등급(`PICKUP_ONCE`는 6성, `RARITY_BY`는 5성)|
|distinct_from_prev|CHAR(1)|NN, 기본 'N'|앞선 보장과 다른 캐릭터여야 하는지(표준·커널의 300회)|
|description|VARCHAR2(500)||인게임 안내 문구 요약|

## 2. 규칙 모델 예시 (명일방주)

게임 안에서 확인한 규칙을 데이터로 넣는 방법이다. 숫자는 인게임 확률 안내를 기준으로 하며, 입력 전에 다시 확인한다. 게임 코드가 아니라 아래 행들이 규칙을 정한다.

### 2.1 공통 기준 데이터
|테이블|행 예시|
|--|--|
|`rarity`|3성(rank 3), 4성(4), 5성(5), 6성(6, is_top='Y')|
|`currency`|오리지늄, 합성옥, 헤드헌팅권, 10회 헤드헌팅권|
|`currency_exchange`|오리지늄 1 → 합성옥 180, 10회 헤드헌팅권 1 → 헤드헌팅권 10|
|`pull_cost`|합성옥 600, 헤드헌팅권 1|
|`pity_group`|standard(표준 헤드헌팅), kernel(커널 헤드헌팅)|

### 2.2 규칙 3가지
|구분|표준 규칙|커널 규칙|콜라보 규칙(포영의 흔적)|
|--|--|--|--|
|`gacha_rule.pity_scope`|GROUP|GROUP|BANNER|
|`gacha_rule.pity_group_id`|standard|kernel|(없음)|
|`pity_rarity_id` / `pity_start_count` / `pity_step_rate`|6성 / 50 / 2|6성 / 50 / 2|6성 / 50 / 2|
|`rule_rate` (기본 확률 / 픽업 몫)|6성 2 / 50, 5성 8 / 50, 4성 50 / 0, 3성 40 / 0|같음|같음|
|`rule_guarantee`|(1) PICKUP_ONCE, 150, 6성<br>(2) PICKUP_ONCE, 300, 6성, distinct_from_prev='Y'|표준과 같음|(1) TARGET_REPEAT, 120, 6성(염호룡 오키드, 획득하면 횟수 다시 시작)<br>(2) RARITY_BY, 50, 5성|
|천장 이어짐|표준 배너끼리 공유, 배너가 끝나도 유지|커널 배너끼리 공유|배너마다 따로, 배너가 끝나면 초기화|

배너의 픽업 인원에 따라 캐릭터별 확률이 정해진다. 예를 들어 표준 배너의 6성 픽업 2명은 `banner_pickup.weight`가 같아서 6성 확률 2% × 픽업 몫 50% ÷ 2명 = 각 0.5%(천장이 없을 때)이다. 5성 픽업 3명은 8% × 50% ÷ 3명이다.

콜라보처럼 배너마다 다른 규칙은 새 `gacha_rule` 행을 만들어 그 배너의 `rule_id`에 연결한다. 일반 한정 배너(신규 6성 2명이 각 35% 등)도 `rule_rate.share_rate`와 `banner_pickup.weight`로 표현할 수 있는지 입력할 때 확인한다.

### 2.3 규칙으로 표현하지 못하는 경우
`rule_guarantee.kind`에 없는 보장은 코드에서 따로 분리해 구현한다(SYS-004). 이때도 게임 이름으로 나누지 않고, 규칙에 `kind`를 추가해 처리한다.

## 3. 남은 확인 사항

|항목|내용|
|--|--|
|규칙 숫자 확인|표준·커널·콜라보의 확률, 천장, 보장 숫자는 인게임 화면으로 확인했다. 일반 한정 배너의 규칙은 아직 인게임 화면으로 확인하지 못했다.|
|`rule_guarantee.kind`|지금 확인한 3종류(`PICKUP_ONCE`, `TARGET_REPEAT`, `RARITY_BY`) 외에 필요한 보장이 있는지 한정 배너 확인 때 점검한다.|
|커널 배너 픽업 선택|계정 연동 라이브러리(ArkPRTS)에 "커널 배너에서 선택한 캐릭터" 항목이 있다. 커널 픽업을 유저마다 고르는 방식이면 회원별 선택 픽업을 저장할 곳이 필요하므로 인게임 규칙 화면으로 확인한다.|
|연동 천장 값|연동으로 6성 천장 카운트를 받을 수 있는지는 실제 응답(`get_raw_data`)으로 확인한다. 받을 수 없으면 천장은 사용자가 직접 입력한다(`pity_state`는 그대로 사용).|
|가져오기 `payload`|공개 데이터의 실제 항목 구성을 확인한 뒤 JSON 구조와 `external_id` 대응을 확정한다.|
|인덱스|조회가 많은 컬럼(`sim_record.member_id, drawn_at`, `banner_schedule`의 기간, `pity_state`)의 인덱스는 테이블 생성 SQL을 쓸 때 정한다.|
|SQL|테이블 생성 스크립트(`테이블_생성.sql`)와 기본 데이터(`기본_데이터.sql`)는 이 설계를 확정한 뒤 작성한다(#8).|
